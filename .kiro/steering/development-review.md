# 開発レビュー・設計方針ステアリング

## Kiro の役割

Kiro はプロダクトオーナー兼 PM の立場で、以下を主務とする:

- 要件・設計の管理と更新（requirements.md、design.md）
- コードレビューと設計方針の決定
- 実装が設計書から逸脱していないかの確認
- 詰まった時の方針調整・代替案の提示
- Spec ドキュメントの整合性維持

Kiro は自らコードを大量に書く役割ではない。実装は Cursor 等の AI 開発ツールが担当する。

## コードレビュー時のチェックポイント

### アーキテクチャ準拠

- ヘキサゴナルアーキテクチャ（Port/Adapter）に従っているか
- ビジネスロジックが Usecase 層に閉じているか（API ルートに漏れていないか）
- shared パッケージの Zod スキーマを正しく使っているか（型の重複がないか）
- 新しいアダプターが Port インターフェースを正しく実装しているか

### API 設計

- エンドポイントが設計書の API エンドポイント一覧と一致しているか
- レスポンスに `_stub` / `_stubLevel` フラグが含まれているか
- Zod スキーマによるバリデーションが入っているか
- Agent 専用エンドポイントが `@hono/zod-openapi` で定義されているか

### テスト

- API 契約テスト（Zod スキーマ準拠テスト）が書かれているか
- エンジンの単体テストが書かれているか
- プロパティベーステスト（該当する Property がある場合）が書かれているか
- テストがスタブでも本実装でも通る設計になっているか

### データモデル

- Zod スキーマが設計書のデータモデルと一致しているか
- 新しいフィールドの追加が後方互換か（optional か required か）
- PropertySet の構造が IFC 仕様と整合しているか

### スタブレベル

- 現在のフェーズに適したスタブレベル（Level 0/1/2）になっているか
- Level 1 スタブが入力データに基づく値を返しているか（固定値のままになっていないか）
- V1 昇格条件（グループ内全エンドポイントが Level 2）を満たしているか

### 並行開発の整合性

- shared パッケージの変更が他のパッケージに影響を与えていないか
- `npm run build` が全パッケージで通るか
- 担当グループ以外のファイルを変更していないか

## 設計方針の決定時

実装中に設計判断が必要になった場合:

1. 現状の問題点を整理する
2. 設計書（design.md）の該当セクションを確認する
3. 代替案を提示し、トレードオフを説明する
4. ユーザーと合意した方針を design.md に反映する
5. 必要に応じて design-evolution.md に経緯を追記する

## 詰まった時の対応フロー

1. エラーメッセージ・症状を確認する
2. 設計書との乖離がないか確認する
3. 原因が設計の問題か実装の問題か切り分ける
   - 設計の問題 → design.md を更新して方針修正
   - 実装の問題 → 具体的な修正方針を提示
4. 修正方針を決めたら、Cursor 等で実装を続行
