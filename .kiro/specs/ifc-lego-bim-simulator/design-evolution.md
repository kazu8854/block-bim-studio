# 要件・設計コンセプトの拡張・整備方針

本ドキュメントは、IFC レゴ BIM シミュレーターの要件定義・技術設計がどのような議論を経て現在の形に至ったかを記録する。他プロジェクトでの参考資料として、「何を考え、なぜそう決めたか」の経緯を残すことを目的とする。

---

## Phase 1: 初期コンセプトの確立

### 出発点
「レゴを組み立てるイメージで建設の IFC ファイルを構成し、ブロックの属性を使って BIM 業務をシミュレーションするアプリ」という一文からスタート。

### 最初の要件定義（10 要件）
- IFC ファイルの読み込み・書き出し
- ブロックパレット、3D キャンバス、属性編集
- 数量算出、コスト概算、干渉チェック
- プロジェクト保存・読み込み、JSON シリアライズ

この時点では「IFC ありき」の設計で、IFC ファイルを読み込んでブロックに変換するのがメインフローだった。

---

## Phase 2: メインフローの転換 ─ 「ブロックから作る」

### ユーザーのフィードバック
> IFC ありきではなく、ブロックから作るっていうのもやりたい。標準的なブロック要素があって、簡単に 3D で組み立てていき、それが IFC として出力・活用できるような形。

### 決定事項
- **メインフロー**: ブロックパレットから選んで 3D で組み立てる
- **IFC 読み込み**: 補助機能に格下げ
- **IFC 書き出し**: 組み立てた結果の出力手段として維持

### 学び
最初から「既存フォーマットありき」で設計すると、ユーザー体験が技術仕様に引きずられる。「ユーザーが何をしたいか」を先に考え、既存フォーマットは入出力の一手段として位置づける方が自然な UX になる。

---

## Phase 3: 工程管理の概念追加

### ユーザーのフィードバック
> 予定的な概念いれるのは難しい？

### 追加した要件（4 要件）
- ブロックの工程情報設定（開始日、終了日、依存関係、進捗状態）
- ガントチャート表示
- クリティカルパス分析
- 4D シミュレーション（時系列アニメーション）

### 学び
BIM の「I」は Information。ブロックに持たせる情報を拡張するだけで、全く新しいシミュレーション領域が開ける。データモデルの拡張性を最初から意識しておくことが重要。

---

## Phase 4: AI 活用と建設業務学習の大幅拡充

### ユーザーのフィードバック
> 建設業の勉強 兼 AI 等でどこまで便利になるかの検証っていう観点だと、何があるとよいと思う？

### 提案 → 全採用（10 要件追加）

**AI 活用系:**
- AI 構造提案（ルールベース/AI）
- 自然言語モデリング（LLM 連携）
- 図面・画像からのブロック生成（画像認識 AI）

**建設業務の学び系:**
- 構造チェック（簡易版）
- 法規チェック（建ぺい率・容積率・避難経路）
- 環境・省エネシミュレーション
- 安全管理シミュレーション

**データ連携・実用系:**
- BIM データのダッシュボード
- 複数プロジェクト比較
- プロジェクト一覧画面の強化

### 学び
「勉強 × 技術検証」というコンセプトが明確になると、機能の取捨選択基準ができる。全部入れても「検証目的」なので、完璧な実装より「動くプロトタイプ」を優先できる。

## Phase 5: 要件のグルーピングと優先順位付け

### ユーザーのフィードバック
> 要件をグルーピングできますか？難易度・有効度から優先順も付けたい。

### 決定事項
24 要件を 6 グループに分類し、各要件に難易度（★〜★★★）、有効度（★〜★★★）、優先度（P1〜P4）を付与。

| グループ | 内容 | 優先度 |
|----------|------|--------|
| A: コア機能 | ブロック操作・属性・プロジェクト管理 | P1 |
| B: BIM シミュレーション | 数量算出・コスト概算・干渉チェック | P2 |
| C: 工程管理 | 工程情報・ガントチャート・クリティカルパス・4D | P2/P3 |
| D: AI 活用 | 構造提案・自然言語モデリング・画像認識 | P3/P4 |
| E: 建設業務チェック | 構造・法規・環境・安全管理 | P3/P4 |
| F: データ連携・分析 | ダッシュボード・IFC 入出力・プロジェクト比較 | P3/P4 |

### 学び
優先度の判断基準を「有効度が高く難易度が低い → P1」と明文化すると、チーム全体で合意が取りやすい。グルーピングは後の並行開発単位にもそのまま使える。

## Phase 7: AgentCore / MCP 統合と AI アダプター抽象化

### ユーザーのフィードバック
> ボイラープレートにもある通り、将来は AgentCore から一部機能を呼ぶような構成へ展開も考えてます。

### 議論の流れ
1. ボイラープレートの README を読み、AgentCore / MCP 統合ガイドの設計思想を確認
2. 既存のヘキサゴナルアーキテクチャ（Port/Adapter）が AI 連携にもそのまま適用できることを確認
3. AI アダプターの抽象化（Bedrock / Ollama / Mock の 3 アダプター）を設計
4. Agent 専用エンドポイント（`/api/agent/*`）を追加
5. OpenAPI スキーマ自動出力（`@hono/zod-openapi`）を追加

### ユーザーのフィードバック（Ollama 連携）
> Mock モードで Ollama とかで Qwen 動かしている場合、そこから呼べるようにできたりする？

### 決定事項
- `MOCK_AWS=true` + Ollama 起動 → OllamaAdapter
- `MOCK_AWS=true` + Ollama 未起動 → MockAIAdapter
- `MOCK_AWS=false` → BedrockAdapter
- 完全オフラインで「AI エージェントが BIM ツールを呼ぶ」体験を検証可能

### 学び
ボイラープレートの設計思想（ヘキサゴナルアーキテクチャ）が、AI 連携の抽象化にもそのまま適用できた。「DB と同じパターンで AI も切り替える」という発想は、既存の設計パターンを知っていれば自然に出てくる。ローカル LLM（Ollama）対応は、開発体験の向上だけでなく、AI エージェント統合の検証環境としても価値がある。

## Phase 8: 並行開発とバージョニング戦略

### ユーザーのフィードバック
> AI 拡張とか順次実装で気にしないといけない部分ってありますか？並行開発もできるような考えは入れておきたい。

### 議論の流れ

**1. インターフェース先行定義の重要性**
- shared の Zod スキーマを「契約」として最初に固める
- フロントエンド・バックエンド・エンジンが並行開発可能に

**2. I/F 変更の連携方法**
> 分散開発して I/F 変更をスムーズに連携する方法とかあります？

- TypeScript のコンパイルエラーが最強の連携ツール
- モノレポ + shared + Hono RPC で「I/F が変わったのに気づかなかった」が構造的に起きない
- CI での全パッケージビルド + テストで自動検出

**3. バージョニング戦略**
> I/F 含むバージョン管理も入れてもいいのかも？

- shared パッケージのセマンティックバージョニング
- Agent API の URL バージョニング（`/api/agent/v1/*`）
- Zod スキーマの破壊的変更時の移行戦略（旧スキーマ deprecated + 変換ユーティリティ）

### 学び
モノレポ + TypeScript + Zod の組み合わせは、分散開発における I/F 変更の連携を構造的に解決する。「コンパイルが通れば整合性が取れている」という保証は、ドキュメントベースの連携より遥かに信頼性が高い。

---

## Phase 9: スタブ戦略と V0/V1 昇格ルール

### ユーザーのフィードバック
> テスト戦略として API ベースでの I/F テストを徹底することが一番重要ですかね。あとは API ごとにスタブなのか、実装なのかどっちを返すかをどのように制御するかもルール化必要？

### 議論の流れ

**1. スタブレベルの定義**
- Level 0: 固定値（型の整合性確認用）
- Level 1: ステートフル/簡易計算（フロントエンド先行開発用）
- Level 2: 本実装

**2. V0 → V1 昇格ルール**
> 全部スタブじゃなくなるタイミングまで V1 にはしないほうが良い？アダプタ内でデータ整合性取れないケースが出てくるってことですよね？

- 機能グループ単位（A〜F）で昇格
- 同じグループ内は必ず同時に昇格（データ整合性のため）
- 異なるグループ間は独立して昇格可能
- `_stub` フラグでスタブか本実装かを判別

**3. フロントエンドの段階的対応**
> フロント的には一部機能が V1 にならないと次の実装できないみたいなケースって出ない？

- MockDbAdapter が Level 1（ステートフル）なので DB 系はブロックされない
- エンジン系は Level 1 スタブ（簡易計算）で「それっぽい値」を返せばフロント開発可能
- 3D レンダリングはバックエンド API と独立なのでフロント内で先行開発可能
- `_stub` フラグで「開発中」バッジを表示する共通パターン

### 学び
「API ファースト」のテスト戦略は、分散開発の基盤になる。API の型（契約）さえ守られていれば、中の実装は自由。スタブレベルの段階的な引き上げにより、フロントエンドが常に「動く状態」を維持できる。

## Phase 10: フェーズ別結合テスト計画

### ユーザーのフィードバック
> 結合テスト（V1 レベル）の想定も入れておいたほうが良いですかね？Ph0 は全スタブ、Ph1 は 3D エンジンの基礎機能＋グループ 1、Ph2 は加えてグループ 2、P3 はそこまでのブラッシュアップ、Ph4 でグループ 3 みたいな感じのざっくり。

### 決定事項

| フェーズ | V1 グループ | 主要テスト観点 |
|----------|-----------|-------------|
| Phase 0 | なし | 型の整合性、契約テスト |
| Phase 1 | A | コア CRUD、3D 基礎、JSON ラウンドトリップ |
| Phase 2 | A, B, C | BIM シミュレーション、工程管理、グループ間連携 |
| Phase 3 | A, B, C（品質向上） | パフォーマンス、エッジケース、UX |
| Phase 4 | A, B, C, D, E, F | AI 連携、建設チェック、データ分析、全体統合 |

### 学び
結合テスト計画をフェーズごとに定義しておくと、各フェーズの「完了」が明確になる。Phase 3 を「ブラッシュアップ」として独立させたのは、新機能追加と品質向上を分離するため。

## Phase 11: マルチ AI ツール対応と Spec 分散開発

### ユーザーのフィードバック
> TASK まではKiro でやりますが、そこからの開発は分散開発を意識しているのでツールが分かれます。基本は生成 AI 開発ツール系です。Claude Code、Cursor、Antigravity、Kiro、Cline...など。組み合わせるケースもあります。

> ボイラープレートでは AI_INSTRUCTIONS でシェアしようとする仕組みをしてましたが、そこが多分リポジトリ作った後の doc で制御する感じになりますかね？その場合も分散開発で doc がコンフリクトしないような仕組みを考えておきたいです。

### 議論の流れ

**1. AI ツール共通ルールの管理**
- ボイラープレートの `AI_INSTRUCTIONS.md` を「全ツール共通の唯一の真実」として継承
- 各ツール固有の設定（.kiro/steering、.cursorrules、.clinerules、CLAUDE.md）は AI_INSTRUCTIONS.md を参照する形で分離
- 補足コンテキスト（ドメイン知識、IFC 仕様）は `docs/ai-context/` に配置して全ツールから参照可能に

**2. Spec ドキュメントのコンフリクト問題**
- tasks.md が最もコンフリクトリスクが高い（タスク着手・完了のたびに更新）
- requirements.md は更新頻度が低くリスク低
- design.md は中程度

**3. コンフリクト回避の3パターン**
- ファイル分割: tasks.md をグループ単位で分割（tasks-group-a.md 〜 tasks-group-f.md）
- セクションオーナーシップ: design.md のセクションごとにオーナーを決める
- Append-Only: design-evolution.md のように追記のみ

**4. タスクステータス更新の規約**
- 着手時に担当者名を記載（`[-] タスク名 @担当者`）して同時着手を防ぐ
- 着手前に最新を pull する運用ルール

### 決定事項
- AI_INSTRUCTIONS.md を全ツール共通ルールとして維持し、ツール固有設定は別ファイルに分離
- tasks.md をグループ単位で分割してコンフリクトを構造的に回避
- requirements.md / design.md の変更は PR + レビュー必須
- 各 AI ツールからの Spec 参照方法を AI_INSTRUCTIONS.md に明記

### 学び
マルチ AI ツール環境では「ルールの一元管理」と「ドキュメントの分割」が鍵。AI_INSTRUCTIONS.md を唯一の真実として、ツール固有設定はそこからの参照にする。ドキュメントのコンフリクトは「同じファイルを複数人が触らない」構造にすることで、運用ルールではなく構造で解決する。

## 全体を通しての学び

1. **ユーザーとの対話で要件は育つ**: 最初の 10 要件が 24 要件 + 8 将来検討に膨らんだ。一度に全部決めるのではなく、対話を通じて段階的に拡充する方が質の高い要件になる。

2. **コンセプトの明確化が取捨選択を助ける**: 「建設業の勉強 × AI 検証」というコンセプトが決まると、何を入れて何を後回しにするかの判断基準ができる。

3. **ボイラープレートの設計思想を活かす**: 既存の設計パターン（ヘキサゴナルアーキテクチャ、Port/Adapter）を新しい領域（AI 連携）にも適用することで、一貫性のある設計になる。

4. **並行開発は設計段階で仕込む**: インターフェース先行定義、スタブレベル、グループ単位の昇格ルールなど、並行開発を可能にする仕組みは後付けでは難しい。設計段階で意識的に組み込む。

5. **型安全は最強の連携ツール**: モノレポ + TypeScript + Zod の組み合わせで、I/F 変更の影響がコンパイル時に全て検出される。ドキュメントベースの連携より遥かに信頼性が高い。

6. **マルチ AI ツール環境はルールの一元管理が鍵**: AI_INSTRUCTIONS.md を「唯一の真実」として、ツール固有設定はそこからの参照にする。ルールが分散すると各ツールの挙動がバラバラになる。

7. **ドキュメントのコンフリクトは構造で解決する**: 「同じファイルを複数人が触らない」ようにファイルを分割する。運用ルール（「触る前に声をかけて」）は守られないが、構造（ファイルが分かれている）は守られる。
